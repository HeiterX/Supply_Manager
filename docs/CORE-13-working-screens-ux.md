# CORE‑13 — Рабочие экраны Supply Manager

Задача [#34](https://github.com/HeiterX/Supply_Manager/issues/34). Ветка основана на CORE‑12, коммит `7d6f6f1` из [PR #43](https://github.com/HeiterX/Supply_Manager/pull/43). После объединения CORE‑12 проверьте diff относительно актуального `main` и переключите базу PR на `main`.

## Рабочий процесс

| Маршрут | Что можно сделать |
| --- | --- |
| `/` | Открыть закупку, создать новую, найти нужную запись, применить серверные фильтры, сортировку или сохранённый вид. |
| `/requests` | Найти заявку, открыть предпросмотр, проверить позиции и фото, принять заявку и перейти к созданной закупке. |
| `/requests/[id]` | Открыть карточку заявки по прямой ссылке. Доступны сведения о заявителе, позициях и результате обработки. |
| `/tasks/[id]` | Перейти между обзором, позициями, предложениями, заказами, оплатами, доставкой и историей. |
| `/request` | Указать заявителя и позиции, приложить фотографии, проверить и отправить заявку. |

Списки используют `WorkingTable` и `WorkingTableControls` поверх компонентов CORE‑12 `TableRegion`, `Field`, `StatusBadge`, `Modal`, `LoadError`, `EmptyState`, `Skeleton` и `Toast`. `PageLayout`, `AppShell` и `AuthGate` сохраняют общую навигацию и ролевой доступ. Для планшетов и компьютеров используются таблицы. На телефонах строки списков отображаются карточками. Сравнение КП, позиции и таблицы отслеживания прокручиваются внутри подписанного региона на узких экранах.

Маршруты хранят фильтры, запрос, сортировку и страницу в URL. Переход в карточку сохраняет безопасную ссылку возврата. При смене параметров отменяется предыдущий запрос, а при загрузке следующей страницы контур текущей таблицы остаётся видимым. «Сохранить вид» записывает фильтры, порядок и размер страницы в localStorage. Поисковая строка и результаты остаются вне хранилища. Текст поиска из URL может попасть в историю браузера.

## Контракты

| Данные | Контракт |
| --- | --- |
| Закупки и заявки | `GET /discovery/lists/tasks`, `GET /discovery/lists/requests` из [CORE‑11 PR #42](https://github.com/HeiterX/Supply_Manager/pull/42). Поиск через `q`; пагинация через `page` и `pageSize`; сортировка через `sort` и `direction`. Быстрые виды используют `view=active`, `overdue=true`, `view=logistics` и `status=CLOSED`. `logistics` означает «В пути» и «Готово к получению» по правилам PR #42. |
| База CORE‑12 | Если discovery отвечает 404, интерфейс использует существующие `GET /tasks` и `GET /purchase-requests`. Старые маршруты возвращают списки целиком. В этом режиме элементы серверной фильтрации и пагинации скрыты. Для крупных реестров требуется CORE‑11. |
| Закупка | `POST /tasks` и `GET /tasks/:id`. История отображает `activities` из ответа сервера. Вкладки имеют URL-параметр `tab`. |
| Карточка заявки | `GET /purchase-requests/:id`, `PATCH /purchase-requests/:id/accept`. В карточке отображаются доступные серверные поля `processedBy`, `processedAt`, `decisionComment` и связанная закупка. |
| Следующее действие | `GET /next-actions/by-task/:id` по контракту [CORE‑09 PR #40](https://github.com/HeiterX/Supply_Manager/pull/40). Если маршрут отсутствует, работает существующее поле `Task.nextAction` и ручное редактирование CORE‑12. При интеграции PR #40 используйте его `TaskNextAction` и слот `AppShell.tools` для центра уведомлений. |
| Позиции и заказы | Существующие маршруты позиций, КП и `POST /tasks/:id/supplier-offers/:offerId/purchase-order`. Транзакция на сервере проверяет остаток и запрещает второй действующий заказ по тому же КП. |
| Фото заявки | `POST /purchase-requests/public`, затем `POST /purchase-requests/public/:requestId/items/:itemId/photo` с `X-Upload-Token`. Для просмотра применяется защищённый `GET /purchase-requests/public/items/:itemId/photo` с cookie. Фото загружается по явному действию в blob URL, который освобождается при закрытии. |
| Оплаты и доставка | `purchaseOrders` из карточки закупки. Вкладки отображают сумму счета в рублях, дату передачи на оплату, факт оплаты, отгрузку, ожидаемое и фактическое поступление, перевозчика и трек. Для старого формата поддерживается `purchaseOrder`. |

## Формы и ошибки

- Публичная форма держит черновик в памяти между шагами. Имя, текст, фото и временный токен остаются вне хранилища браузера. При выходе со страницы с черновиком браузер запрашивает подтверждение. Фото отправляются после подтверждения регистрации заявки. Если фотография не загрузилась, можно повторить загрузку в текущем сеансе, используя токен выданный для этой заявки.
- Заказ открывается из выбранного КП. Шаги проводят через позиции и количества, реквизиты счёта и сверку перед подтверждением. Сумма предпросмотра считается в копейках и тысячных долях количества. Ставки и сроки берутся из самого КП. Итоговую сумму определяет сервер. Даты редактируются в местном времени и передаются в ISO 8601. Календарные даты в списках отображаются в `Europe/Moscow`.
- Ошибки полей связаны с контролами. Формы сохраняют ввод при ошибках. Синхронная блокировка подавляет повторный submit. При 409 в заказе карточка перечитывается, введённые данные сохраняются, а изменившийся остаток заново проверяется перед повтором. При потере ответа на создание закупки или публичной заявки отправка блокируется до проверки результата.
- Распределение позиций складывает количества действующих заказов в тысячных. Приход учитывается по факту получения заказа. Остаток к заказу и остаток к получению показаны отдельно. Отменённые заказы остаются в списках и истории.

## Зависимости

- CORE‑11 должен попасть в целевую ветку для поиска и пагинации на реальном сервере. Два независимых PR изменяют корневой список и список заявок. При объединении сохраните текущую рабочую раскладку, подключите общий клиент discovery из CORE‑11 и сохраните его глобальный поиск, аналитику, экспорт и дополнительные маршруты.
- CORE‑09 предоставляет UI уведомлений и операций Next Action. Запись, завершение и отдельная история действий требуют соответствующих серверных маршрутов.
- В текущих контрактах отсутствуют фильтр «Мои закупки», ответственный закупки в списке, подразделение в публичной заявке, отказ и запрос уточнения заявки, файлы КП и счетов, оплата траншами, частичная приёмка внутри заказа и публичный ключ идемпотентности. Для частичной доставки можно отслеживать отдельно полученные заказы. Начальный статус, приоритет и срок публичной заявки определяет сервер.
- Сценарий создания через необновлённое КП старого формата сохраняет штатный диалог. Новый заказ с распределением позиций использует мастер.

## Проверки и воспроизведение

`npm ci`, `npm run lint` и `npm run build` для Web. API lint/build, Prisma generate, 2 unit и 30 E2E. E2E выполнялись с четырнадцатью миграциями на отдельном PostgreSQL 17, схема `e2e`.

Для браузерных тестов запустите production build на порту 3391 и выполните `node --test apps/web/test/core13.browser.mjs`. Нужен Playwright, установленный в окружении проверок. Можно указать его путь в `CORE13_PLAYWRIGHT`, выбрать установленный Chrome через `CORE13_BROWSER_CHANNEL=chrome` и задать каталог снимков через `CORE13_SCREENSHOTS`. `CORE13_WEB` принимает локальный адрес Web. Сценарии с синтетическими ответами проверяют URL-фильтры, пагинацию, сохранение вида, восстановление контекста, 404/403, фото, 409 заказа, повтор фото, потерю соединения и блокировку дублей. Проверяются ширины 375, 390, 768, 1024, 1440 и 1920 CSS px.

В итоговом прогоне Chrome прошли все 7 тестов и вложенных сценариев, включая сквозной проход с реальными NestJS, cookie и PostgreSQL. Для воспроизведения сквозного прохода используйте пустой локальный PostgreSQL 17 на `127.0.0.1:55433` с тестовой базой и пользователем `core13_local`, примените миграции в схеме `e2e`, запустите NestJS на порту 3390 и соберите Web с `NEXT_PUBLIC_API_URL=http://127.0.0.1:3390/api/v1`. Укажите origin Web в `FRONTEND_ORIGIN` API и выполните тест с `CORE13_REAL_API=1`. Сценарий регистрирует тестового снабженца, отправляет заявку с синтетическим PNG, проверяет фото через cookie, принимает заявку, сравнивает два КП и оформляет заказ на часть позиций.

При ревью пройдите цепочку «Публичная заявка с фото → принятие → закупка → два КП с пересекающимися позициями → частичный заказ → оплата → доставка → история». В двух сеансах попробуйте оформить перекрывающиеся количества. Проверьте возврат из карточки, Escape и возврат фокуса из предпросмотра, а также использование формы сотрудником без доступа к закупкам.
