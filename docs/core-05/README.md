# CORE-05 — Позиции закупки и единая номенклатура

Задача: [#26](https://github.com/HeiterX/Supply_Manager/issues/26).

## Назначение

Номенклатурная карточка — повторно используемый справочник, а не исходная
потребность сотрудника. Поля позиции закупки хранятся отдельно и сохраняют
первичную спецификацию даже при изменении справочника.

## Модель данных

- `CatalogItem`: наименование, артикул, категория, единица, технические
  характеристики (JSON), отпечаток для защиты от дублей, дата создания.
- `TaskItem`: catalogItemId (опционально), sourceRequestItemId (опционально),
  originalSnapshot (неизменяемый первичный снимок), technicalParameters,
  requiredAt, а также прежние наименование, артикул, количество, единица, цена,
  примечание и порядок строки.
- `TaskItemChange`: CREATE/UPDATE/DELETE, исполнитель, дата, снимки до и
  после изменения. История не удаляется при удалении незадействованной позиции,
  так как связана с Task.
- `PurchaseRequestItem`: хранит исходное требование и фотографии. При
  преобразовании в закупку сохраняется отдельная ссылка и снимок.

Миграция `20261123190000_core05_catalog_task_items` добавляет только новые
таблицы/nullable-поля, существующие позиции не переписываются.

## Уникальность и варианты

Fingerprint SHA-256 формируется из категории, нормализованного артикула
(если его нет — наименования), единицы и нормализованной сортированной пары
«характеристика: значение». Пробелы и регистр не создают новую карточку.
Другие варианты технических характеристик допускаются отдельно. Дубль —
HTTP 409, ссылку на найденную карточку предоставляет API.

Единицы не конвертируются автоматически. Коды и значения должны
быть технически совместимы; создание дубликатов с другой единицей не
рассматривается как эквивалентность.

## Правила работы с позицией

При выборе справочника для **новой** позиции frontend предлагает значения
поля наименования, артикула, единицы и параметров. При выборе для
**существующей** позиции данные не подменяются; API проверяет точное
соответствие артикула/наименования, единицы и характеристик.

При несовпадении выдается HTTP 409. Подмена аналогом без внешнего
документированного технического согласования в CORE-05 не поддерживается.
Искусственного «автоматического согласования» здесь нет.

После появления хотя бы одной строки КП или заказа, включая отменённые,
редактирование и удаление позиции запрещены: HTTP 409. Создание КП
синхронизировано с редактированием позиций транзакционной блокировкой Task.
Создание заказа использует тот же порядок блокировок, сохраняя учёт
количеств и целостность FK.

## Прогресс

В `GET /api/v1/tasks/:id` у каждой позиции есть `progress`:

- `required` — количество потребности;
- `offered` — максимум по активным КП (не сумма альтернатив);
- `ordered` — сумма неотменённых заказов;
- `received` — сумма строк заказов в RECEIVED/HANDED_OVER;
- `handedOver` — сумма строк заказов в HANDED_OVER.

Исторические legacy-заказы без строк не влияют на количественный прогресс.
Расчёт делается из существующих `SupplierOfferItem` /
`PurchaseOrderItem`, без дополнительного хранимого счётчика.

## API (PROCUREMENT/ADMIN)

- `GET /api/v1/catalog?q=...` — поиск (до 50 записей);
- `POST /api/v1/catalog` — создание карточки;
- `GET /api/v1/catalog/:id` — просмотр карточки;
- `POST /api/v1/tasks/:id/items` — создать позицию/связать справочник;
- `PATCH /api/v1/tasks/:id/items/:itemId` — изменить до КП и заказов;
- `DELETE /api/v1/tasks/:id/items/:itemId` — удалить до КП и заказов;
- `GET /api/v1/tasks/:id/items/:itemId/history` — история позиции;
- `GET /api/v1/tasks/:id` — агрегированный прогресс и аудит.

Роли проверяются сервером. Для изменяющих запросов с cookie-сессией
действует защита CORE-03 (CSRF).

## Проверки

Из каталога проекта:

```bash
cd apps/api
npx prisma format
npx prisma generate
npm run lint
npm run build
npm run test:e2e
cd ../web
npm run lint
npm run build
```

E2E всегда запускать через `npm run test:e2e`: он проверяет отдельную
схему `e2e`. Не использовать `prisma migrate reset` и не запускать
`npx vitest` напрямую на рабочей базе. Для dev-схемы сначала создать
резервную копию и выполнить `prisma migrate deploy`.

## Зависимости и контроль выпуска

Ветка CORE-05 основана на CORE-04. Перед слиянием в main необходимо
слияние зависимых PR CORE-03 и CORE-04, ревью Тимофея, E2E и
ручной smoke-test на синтетических позициях и заказах.
