# CORE-07 — Многопоставочные заказы и контроль распределения количеств

Issue: https://github.com/HeiterX/Supply_Manager/issues/28
Ветка: `feature/core-07-multi-orders-allocation`
База: CORE-06 (`feature/core-06-suppliers-offers`)

## Задача

Один Task содержит несколько коммерческих предложений SupplierOffer и
несколько PurchaseOrder, по одному у разных поставщиков. Каждая строка заказа
PurchaseOrderItem хранит исходный `taskItemId`, строку КП и snapshot
количества, цены, артикула и единицы.

## Основные инварианты

- Сумма количеств всех **неотменённых** заказов по TaskItem не может превышать
  требуемое количество TaskItem.quantity. Числа проверяются с точностью 0.001.
- Учитываются все действующие статусы заказов, в том числе ожидающие оплаты.
- Отменённые заказы не занимают доступный остаток, но остаются в истории.
- Счёт и количество нельзя менять после подтверждения оплаты или отгрузки.
- Нельзя изменить состав исходной позиции после появления связанных строк КП.
- Нельзя использовать строку не того КП или другой закупки.
- Заказ создаётся только по выбранному КП (ручное решение CORE-06),
  валюта — RUB. Поставщик должен быть активен, срок КП не истёк.
- Старые заказы без детализации строк не смешиваются с новым механизмом.
- Отрицательный остаток или повторное резервирование запрещены на уровне API.

## Атомарность

`MultiOrdersService.lockTask()` использует `SELECT ... FOR UPDATE`
в PostgreSQL в рамках той же транзакции, что и создание, изменение,
отмена или изменение статуса заказа. Для операций по одной закупке
резервирование сериализуется: второй запрос работает с уже обновлённым
составом заказов и получает HTTP 409 при превышении остатка.

## Идемпотентность создания

`POST /api/v1/tasks/:taskId/supplier-offers/:offerId/purchase-order` может
принимать `idempotencyKey` (UUID v4). Клиент создаёт ключ для одного
действия и повторяет **тот же ключ с тем же телом запроса** после
таймаута или сетевого обрыва.

В PostgreSQL добавлено уникальное ограничение
`UNIQUE(taskId, idempotencyKey)`; к сохранённому заказу добавлен
`requestFingerprint` (SHA-256 по поставщику/КП, счёту, строкам,
количествам и примечанию). Повтор с тем же содержимым возвращает
существующий заказ (в том числе впоследствии отменённый). Повтор с
другим содержимым и тем же ключом возвращает HTTP 409.
Ключ опциональный для совместимости со старым API, однако
новый интерфейс его всегда передаёт.

## Редактирование до оплаты

`PATCH /api/v1/tasks/:taskId/orders/:orderId`:
- обязательный `expectedVersion` (целое число) и новый непустой `items`;
- опционально номер/дата счёта, примечание;
- разрешено только для активных статусов ORDERED, WAITING_PAYMENT,
  без paidAt / shippedAt / cancelledAt;
- расчёт остатков исключает текущий заказ и заново проверяет позиции;
- строки заменяются целиком транзакционно;
- если счёт уже передавался на оплату, статус возвращается в ORDERED,
  `sentToPaymentAt` сбрасывается — новый счёт нужно отправить повторно;
- инкремент `version`, snapshot до/после и запись об изменении в истории;
- при устаревшей версии HTTP 409, старый заказ сохраняется без изменений.

## Отмена и жизненный цикл

`PATCH /api/v1/tasks/:taskId/orders/:orderId/cancel` требует
непустую причину. Разрешено только до оплаты и отгрузки
(ORDERED/WAITING_PAYMENT). Отмена ставит cancelledAt, cancelReason,
сохраняет `PurchaseOrderRevision`, инкрементирует версию, обновляет
статус закупки и освобождает всю заказанную позицию для нового заказа.
Повторная отмена даёт HTTP 409.

Переходы статусов сохраняют отдельные версии/снимки;
после оплаты редактирование и отмена запрещены.
Закупка закрывается, только когда вся потребность передана
получателям, а все действующие заказы дошли до HANDED_OVER.

## Серверный расчёт распределения

`GET /api/v1/tasks/:taskId/allocation` возвращает для каждой позиции:

- `required` — исходная потребность;
- `reserved` — часть действующих заказов в ORDERED / WAITING_PAYMENT;
- `ordered` — все неотменённые заказы **включая reserved**;
- `paidOrLater` — действующие заказы после оплаты (не прибавлять к ordered);
- `cancelled` — историческая сумма отменённых заказов,
  включая многократные попытки;
- `available` = max(0, required − ordered);
- `bySupplier` — разрез по поставщику, заказу, статусу и количеству.

`GET /api/v1/tasks/:id` теперь также включает
reserved, cancelled и available в `items[].progress`.
Резерв **не нужно повторно прибавлять** к ordered.

## Интерфейс

В `/tasks/[id]`:
- таблица и полосы распределения;
- резерв, отменённые количества, свободный остаток;
- разбивка по поставщикам;
- кнопка «Изменить до оплаты» с заполнением существующих строк;
- создание заказа с UUID-ключом повтора;
- история `PurchaseOrderRevision` с версией, действием, исполнителем
  и снимками до/после;
- блокировка кнопок в запрещённых статусах.

## Миграция

`20261124120000_core07_order_allocation` добавляет nullable
`idempotencyKey` и `requestFingerprint`, `version` с default 1 и
таблицу `PurchaseOrderRevision`. Существующие заказы не изменяются
и не удаляются. В PostgreSQL уникальные NULL-ключи не мешают
историческим заказам без idempotencyKey.

## Проверки и безопасный запуск

```bash
cd apps/api
npx prisma generate
npm run lint
npm run build
npm run test:e2e
cd ../web
npm run lint
npm run build
```

E2E запускаются **только** из `npm run test:e2e`, который
проверяет изоляцию `?schema=e2e` и применяет миграции
к тестовой схеме PostgreSQL. Не запускать `npx vitest` напрямую
на базе разработки. В dev перед миграцией нужен backup.

Новый E2E: `apps/api/test/core07-allocation.e2e-spec.ts`.
Покрывает разные источники КП, частичное распределение, идемпотентный
повтор и конфликт ключа, конкурирующие создания двух снабженцев,
редактирование количества, stale version, сброс статуса оплаты,
отмену, права доступа и отрицательные случаи.
