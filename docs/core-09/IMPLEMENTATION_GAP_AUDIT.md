# CORE-09 — проверка требований и исправление потери напоминаний

Срез: 26.11.2026. Основание: [Issue #30](https://github.com/HeiterX/Supply_Manager/issues/30), исходный CORE v3.0 от 19.11.2026, контракт UI из [PR #40](https://github.com/HeiterX/Supply_Manager/pull/40) и фактический код `main`.

## Исправленный дефект (этот PR)

`MultiOrdersService.refreshTask()` раньше на **каждом** обновлении статуса многопоставочной закупки записывал `reminderAt: null`, даже когда пользователь не менял напоминание. Это нарушало требование CORE-09 «не терять напоминание при обновлениях». Теперь поле не трогается при переходах заказов; явное завершение закупки в `closeTask()` по-прежнему очищает `reminderAt` и `nextAction`.

Добавлен E2E-тест в `core07-allocation.e2e-spec.ts`: установить напоминание → создать заказ → проверить дату → отменить заказ до оплаты → проверить сохранение даты. Не добавляются новые модели, не меняется схема БД, существующие данные не мигрируют.

## Уточнённые доменные правила

1. `Task.deadline` остаётся общим сроком закупки. `NextAction.dueAt` — крайний срок конкретной операции. `reminderAt` не равен ни одному из этих сроков.
2. Ответственный должен быть активным пользователем с ролью PROCUREMENT или ADMIN. Назначение или чтение чужих действий — только по явно согласованным полномочиям, не по наличию любого cookie.
3. Сервер, а не браузер, определяет overdue/today/ожидание поставщика; дневные границы и рабочее время необходимо утвердить. Перенос действия инвалидирует предыдущие ещё не отправленные события.
4. При завершении/отмене закупки нельзя создавать новые напоминания по старому действию. Исторические события сохраняются.
5. Обновления происходят по optimistic version + idempotency key, в транзакции с проверкой текущего lifecycle; повтор после таймаута не должен создать вторую запись/уведомление.
6. Web-уведомления и Telegram не рассылаются всем снабженцам по умолчанию: доступ и адресаты проверяются сервером. Скрытые/отключённые подписки и блокировка роли учитываются повторно перед доставкой.
7. Старые закупки без явного assignee нельзя автоматически приписывать случайному пользователю: требуется контролируемая процедура первичного назначения или очередь «требуется назначение».
8. Не смешивать изменение статуса заказа (CORE-07/08) с изменением срока/ответственного Next Action. Дальнейшая интеграция должна убрать перезапись описания действия при `refreshTask()`, сохранив текущие подсказки как *производные*, пока отдельной сущности нет.

## Минимальная последовательность дальнейшей реализации

- Согласовать точный контракт `docs/CORE-09-ui-api-contract.md` из PR #40, включая `If-Match`, `Idempotency-Key`, поля assignee/dueAt/reminderAt и 409.
- Добавить **аддитивную** миграцию таблиц действий, истории, событий и пользовательских уведомлений без сброса БД; подготовить безопасное назначение для legacy-закупок.
- Реализовать серверные `GET /next-actions`, `GET /next-actions/by-task/:taskId`, `PATCH /next-actions/:id`, историю, `GET /notifications`, `PATCH .../read`.
- Реализовать планировщик и transactional outbox: уникальный ключ события по действию/версии/этапу, повторный контроль актуальности и подписки при отправке, без обещания exactly-once Telegram.
- Адаптировать UI PR #40 на текущий AppShell, интегрировать с CORE-10 и CORE-11, проверить фильтры и счётчики.
- E2E: 401/403/чужой taskId, перенос после напоминания, конкурентный PATCH, дубль idempotency-key, DST/time zone, остановка при CLOSED/CANCELLED, multi-supplier order без потери даты; ручной smoke-test с синтетическими данными.

**Статус:** только целевой дефект `reminderAt` исправлен в этом PR. CORE-09 в целом не завершён, Issue #30 оставлять открытым до полноценной реализации и бизнес-приёмки. До этого нельзя обещать персональные напоминания и автоматическое определение просрочки.
