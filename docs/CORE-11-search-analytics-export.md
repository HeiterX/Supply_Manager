# CORE-11 — Поиск, фильтры, аналитика и экспорт

Задача [#32](https://github.com/HeiterX/Supply_Manager/issues/32). База разработки — `origin/main` на `aa70d7f`. Поиск, списки и выгрузка используют одни серверные фильтры поверх существующих моделей Prisma. [Схема архитектуры](core11-discovery.puml).

## API

Все маршруты ниже находятся под `/api/v1/discovery` и требуют действующей cookie-сессии. Ответы имеют `Cache-Control: private, no-store`.

| Метод и путь | Ответ |
| --- | --- |
| `GET /search?q=…` | Страница результатов с `entity`, `id`, `title`, `reference`, `href`. Пустой или состоящий из пробелов запрос возвращает пустую страницу. |
| `GET /lists/:entity` | Страница строк. Типы `tasks`, `items`, `suppliers`, `orders`, `requests`. |
| `GET /lists/:entity/export?format=csv` | Файл всей отфильтрованной выборки. Второй формат — `xlsx`. |
| `GET /task-overview` | Счётчики закупок и шесть закупок, требующих внимания, по действующим признакам рабочего списка. |
| `GET /suppliers/:id` | Контакты поставщика. История заказов запрашивается через `/lists/orders?supplierId=:id`. |
| `GET /analytics?from=2026-01-01&to=2026-03-31` | Снимок закупок, метрики событий за период, месячные ряды, статусы заказов, сводка поставщиков, просроченные закупки и список недоступных показателей. |
| `GET /analytics/export?format=xlsx&from=…&to=…` | Те же разделы отчёта в табличном файле. |

Страница имеет `{items,total,page,pageSize,hasPrevious,hasNext}`. Нумерация с 1, размер по умолчанию 25 (максимум 100), максимальный номер страницы 10 000. Сортировка списка по умолчанию `createdAt desc, id asc`. У nullable-полей срока и номера счёта пустые значения помещаются в конец. Каждая страница и её `total` считываются в одной транзакции `REPEATABLE READ`. Изменения между отдельными HTTP-запросами могут изменить offset-выдачу.

Глобальная поисковая выдача последовательно группируется по типу (закупки, позиции, поставщики, заказы, заявки) и в группе сортируется по дате создания и ID. Регистронезависимое подстрочное совпадение использует PostgreSQL `ILIKE` и Unicode-локаль БД. Литеральные `%`, `_` и обратная косая черта экранируются. Запрос до 120 символов, управляющие символы отклоняются. Чисто цифровой запрос или номер с `#` сравнивается и с текстовым представлением номера. Если совпадений по номерам больше 10 000 на сущность, API просит уточнить запрос. В заказах используется ID или номер счёта.

## Поля поиска и фильтры

Во всех списках доступны `q`, `createdFrom`, `createdTo`, параметры сортировки `sort`, `direction=asc|desc` и пагинации. Диапазоны принимают даты `YYYY-MM-DD`, включают указанные дни по Москве и вычисляются через полуоткрытые интервалы. Ошибка в значении, диапазоне, поле сортировки или неприменимом фильтре возвращает HTTP 400.

| Сущность | Поисковые поля | Дополнительные фильтры | Сортировка |
| --- | --- | --- | --- |
| Закупки | Номер, заголовок, описание, статус, текст существующего поля следующего действия | `view=active\|attention\|logistics`, `status`, `priority`, `deadlineFrom/To`, `overdue`, `supplier`, `hasOrders`, `payment`, `delivery` | `createdAt`, `deadline`, `priority`, `status`, `number`, `name` |
| Позиции | Название, артикул, примечание, номер и название закупки, связанные поставщики | Фильтры закупки, включая статус и плановый срок, кроме `view`. Дата создания относится к позиции | Как у закупки, `name` означает название позиции |
| Поставщики | Название, ID, контакт, телефон, email, сайт | Общие фильтры | `createdAt`, `name` |
| Заказы | ID, номер счёта, трек-номер, статус, поставщик, номер и название закупки | `status`, `deadlineFrom/To` по ожидаемому прибытию, `overdue`, `supplier`, `supplierId`, `payment`, `delivery` | `createdAt`, `deadline`, `status`, `number` по номеру счёта, `name` по поставщику |
| Заявки | Номер, заголовок, инициатор, статус, названия и артикулы позиций | `status`, `priority`, `deadlineFrom/To` по `requiredAt` | `createdAt`, `deadline`, `priority`, `status`, `number`, `name` |

`supplier` ищет подстроку имени. Для закупок без фильтра по оплате или доставке учитываются поставщики из КП и заказов. С фильтрами по заказам имя, оплата и статус доставки относятся к одному заказу. `hasOrders=true` включает исторические и отменённые заказы. `payment=paid|unpaid` опирается на наличие `paidAt` у действующих заказов. `delivery` принимает существующий `PurchaseOrderStatus`. Для `overdue` и `hasOrders` принимаются `true` и `false`.

Списки закупок, заявок и позиций доработаны на существующих маршрутах. В AppShell добавлен единый поиск с задержкой 300 мс и отменой предыдущего запроса. Фильтры живут в URL. Обратная ссылка из карточки закупки принимает только внутренние маршруты приложения. В списке заявок позиции открываются по запросу при раскрытии карточки, с существующим маршрутом приёма заявки и доступа к фото. У заказов и поставщиков появились отдельные списки, у поставщика — карточка с историей заказов.

## Права и защита данных

`JwtAuthGuard` проверяет активную учётную запись. Закупки, позиции, поставщики, заказы и аналитика доступны ADMIN и PROCUREMENT согласно существующей матрице. EMPLOYEE видит исключительно собственные заявки, идентифицированные по `requesterId`. Общий поиск сотрудника, `total` и экспорт используют этот предикат до формирования ответа. Заявки без зарегистрированного инициатора видны снабжению и администратору.

Запросы Prisma и участки SQL параметризованы. Для SQL-идентификаторов разрешены только имена таблиц из кода и экранированное серверное имя схемы Prisma. Сортировка реализована через соответствия полям моделей. Выгрузки формируются из явно перечисленных столбцов. Хеши паролей, Telegram ID, пути к файлам и внутренние примечания в выгрузки не включены.

## Определения отчёта

По умолчанию период — 90 календарных дней, включая текущий день. Максимум 366 дней. Срез фиксируется на момент запроса. Сервер принимает календарные даты по `Europe/Moscow`, хранит время по UTC и группирует события по месяцу в московской зоне.

- **Снимок закупок.** Активные исключают `CLOSED` и `CANCELLED`. Просрочка закупки означает `deadline < now` у активной закупки. Закупка ожидает поставки, когда у неё хотя бы один заказ в `WAITING_SHIPMENT`, `IN_TRANSIT` или `READY_FOR_PICKUP`. Одна закупка считается один раз. Таблица просрочек показывает 25 ближайших по порядку срока и ID.
- **События периода.** Заявки и созданные закупки считаются по `createdAt`, закрытые закупки по `closedAt` в статусе `CLOSED`, заказы по `orderedAt`. Получение считается по `receivedAt` в статусе `RECEIVED` или `HANDED_OVER`. Статусы заказов в отчёте отражают текущее состояние заказов, оформленных за выбранный период. Просрочка прибытия в этой когорте означает ожидаемое прибытие в прошлом у ещё не прибывшего заказа на этапе оформления, оплаты, отгрузки или пути.
- **Оплаты.** Сумма заказов со счётом использует `totalPrice` по `invoiceDate`, подтверждённая оплата — по `paidAt`, неоплаченные заказы со счётом — `invoiceDate` в периоде и `paidAt IS NULL`. Отменённые заказы исключены. Суммы вычисляет PostgreSQL `numeric`, в JSON они передаются строками. Счета и подтверждения без суммы считаются отдельно. В текущей модели сумма заказа и доставки ведётся в RUB. Валюта позиции сохраняется отдельно. Конвертация валют отсутствует.
- **Поставщики.** До 25 поставщиков по числу действующих заказов, сортировка по числу заказов и ID. Сумма берётся на уровне заказов, включая доставку. Доля опоздавших относится к полученным заказам с известным планом и фактом. Факт прибытия берётся из `readyForPickupAt`, при его отсутствии из `receivedAt`. Поставщик с нулевым числом измеримых заказов отображается без процента.

## Формат файлов

CSV использует UTF-8 с BOM, разделитель `;`, десятичную запятую у числовых полей, CRLF и удвоение кавычек внутри заключённых в кавычки строк. Даты представлены в московском времени в виде `YYYY-MM-DD HH:mm:ss`. Пустые значения занимают пустую ячейку. Потенциально опасный текст, включая формулу после пробелов или невидимых форматирующих символов, экранируется начальным апострофом.

В XLSX пользовательские строки имеют тип текста. Даты и числа используют типизированные ячейки. Десятичные значения, которые превышают точность Excel в 15 цифр, сохраняются как точный текст. Суммы сопровождает отдельная колонка валюты. Имя файла содержит тип выборки и московскую дату формирования.

Лимит экспорта списков — 2 000 строк, лимит текста в выгрузке — 4 МиБ, лимит ячейки — 32 767 символов. При превышении сервер возвращает 413. На экземпляр API одновременно выполняется до двух генераций. При занятых слотах возвращается 503. Страница из URL не ограничивает экспорт. Данные ограничиваются до кодирования и пишутся в один буфер без фоновых задач.

## Проверка

Требования — Node 24, установленные зависимости обеих частей и локальный PostgreSQL 17. Для E2E применяется отдельная база со схемой `e2e` и тестовым JWT. См. [настройку проекта](../README.md) и `apps/api/.env.example`.

1. В `apps/api` выполните `npm ci`, `npx prisma generate`, `npm run lint`, `npm run build`, `npm test`.
2. Настройте `apps/api/.env.test` с изолированным URL и выполните `npm run test:e2e`. При запуске через PowerShell после проверки изоляции установите `NODE_ENV=test`, `DATABASE_URL` с `?schema=e2e` и тестовый `JWT_SECRET`. Затем выполните `npx prisma migrate deploy` и `npx vitest run --config vitest.config.e2e.ts`.
3. В `apps/web` выполните `npm ci`, `npm run lint`, `npm run build`.
4. Для браузерных E2E запустите собранный API с тестовыми переменными, `PORT=3380` и `FRONTEND_ORIGIN=http://localhost:3381`. Соберите Web с `NEXT_PUBLIC_API_URL=http://localhost:3380/api/v1`, запустите `npm run start -- -p 3381`. Установите Chromium командой `npx playwright install chromium` или укажите `CORE11_BROWSER_CHANNEL=chrome` для установленного Chrome. Выполните `npm run test:browser` из `apps/web` с тем же изолированным `DATABASE_URL`. Скрипт добавляет и удаляет синтетические записи. На тестовом сервере не должно быть реальных данных.

Синтетический PostgreSQL 17, `EXPLAIN ANALYZE`, выборка страницы и отдельный `count(*)` по подстроке двух полей. На 1 000 закупок — 0,45 мс и 0,38 мс. На 25 000 — 10,52 мс и 11,43 мс. Поиск подстроки использовал последовательное чтение, селективный фильтр статуса — `Task_status_idx` (0,02 мс на 25 000). Это серверное время конкретных запросов на локальном наборе, размер страницы 25. Нужда в дополнительных индексах для поисковых строк зависит от объёма и смеси реальных запросов. Prisma-миграций CORE-11 нет.

Локально прошли lint и production build API и Web, 6 unit-тестов и 35 HTTP E2E. Пройдены 14 существующих миграций на пустой схеме PostgreSQL 17. API E2E проверяют роль и владение, литеральный поиск, пакет из 2 001 записи, границу суток, точную сумму, экспорт и сверку отчёта. Unit-тесты проверяют входные параметры, формулы, ZIP/XML книги, типы дат и лимиты файлов. В headless Chrome через Playwright прошли четыре браузерных сценария. Проверены cookie-вход, RBAC, фильтры и URL, поиск с отменой запросов, выгрузка обоих форматов, переходы и отсутствие горизонтальной прокрутки страницы аналитики на 390 × 844. Общие проверки CI зависят от состояния [CORE-02, PR #39](https://github.com/HeiterX/Supply_Manager/pull/39).
