# CORE-15 / #59 — проверяемый backup/restore (первый срез)

**Цель:** согласованно сохранять PostgreSQL 17 (supply_manager, public) вместе с приватными вложениями и восстанавливать только в чистую независимую среду. Инструмент не изменяет текущую БД, не выполняет миграции и ничего не удаляет из основного хранилища.

**Статус:** первый этап CORE-15, а не готовность к production и не завершение Issue #36.

## Реальная инвентаризация

| Данные | Путь при запуске API из apps/api | Метаданные БД | Контроль выдачи |
| --- | --- | --- | --- |
| Фото заявок | apps/api/uploads/purchase-requests/ | PurchaseRequestItem.photoPath | JWT; владелец или PROCUREMENT/ADMIN |
| Документы КП: PDF/JPEG/PNG | apps/api/uploads/offer-documents/ | SupplierOfferDocument.storageName, sha256, version | JWT + PROCUREMENT/ADMIN |
| Счета/платежи/приёмка CORE-08 | Файловые вложения ещё не реализованы | Invoice, Payment, Shipment | Структурированные записи; финансовые операции ADMIN при включении feature-flag |

В коде уже используются короткоживущая подпись загрузки фото, обработка sharp, проверка содержимого/MIME КП и имена файлов, генерируемые сервером; в E2E проверены отрицательные права. Оба каталога не должны раздаваться nginx/Next.js как public или помещаться в Git. Пути считаются относительно process.cwd() процесса API, поэтому для backup укажите его фактический каталог uploads, а не случайный checkout. Область будущего аудита выдач файлов и финансовых документов пока не завершена.

## Перед началом

1. Docker и Node.js 24+ доступны в WSL. Основной Postgres запущен как supply-manager-postgres, PostgreSQL 17.
2. **Остановить все API и фоновые процессы, способные писать в БД или файлы**. Не загружать документы одновременно с backup. --writes-paused — подтверждение оператора; скрипт не останавливает писателей автоматически. Без остановки снимок файлов и БД нельзя считать согласованным.
3. Убедиться, что есть отдельная уже проверенная копия на другом носителе. Новый backup создаётся вне каталога Git с правами 0700 на каталоги и 0600 на файлы.

## Снимок базы и вложений

Из корня актуального проекта:

    cd ~/projects/supply-manager-updated
    mkdir -p ~/supply-manager-backups
    chmod 700 ~/supply-manager-backups

    node scripts/core15-snapshot.mjs backup \
      --source-container supply-manager-postgres \
      --uploads "$PWD/apps/api/uploads" \
      --out "$HOME/supply-manager-backups" \
      --writes-paused

В выводе появится путь к новому каталогу core15-..., содержащему database.dump, manifest.json и при наличии два каталога вложений. Существующий backup не перезаписывается. Во время создания сверяются все ссылки на фото/КП в PostgreSQL, размеры, хеши SHA-256, набор счётчиков и неизменность ссылок после копирования. Если исходный файл отсутствует или имя опасно, снимок не публикуется. PostgreSQL dump дополнительно проходит pg_restore --list.

Выполнить проверку (подставить имя созданного каталога):

    SNAPSHOT="$HOME/supply-manager-backups/<имя_созданного_core15_каталога>"
    node scripts/core15-snapshot.mjs verify --snapshot "$SNAPSHOT"

Команда verify работает без подключения к БД. Проверяет размер, SHA-256, имена и отсутствие дубликатов. Хеши позволяют найти случайную порчу, но не гарантируют подлинность против атакующего с доступом на запись к manifest и архиву одновременно. На production требуются отдельные ключи, подпись, внешняя зашифрованная копия и управление доступом. Не прикладывать backup к Issues, PR, сообщениям и CI artifacts.

## Восстановление только в отдельную новую БД

Выполнить из WSL:

    docker run -d \
      --name supply-core15-restore \
      -e POSTGRES_USER=supply_restore \
      -e POSTGRES_PASSWORD=restore_test_only_password \
      -e POSTGRES_DB=supply_core15_restore \
      -p 127.0.0.1:55443:5432 \
      postgres:17-alpine

    docker exec supply-core15-restore \
      pg_isready -U supply_restore -d supply_core15_restore

    cd ~/projects/supply-manager-updated

    node scripts/core15-snapshot.mjs restore \
      --snapshot "$SNAPSHOT" \
      --target-container supply-core15-restore \
      --target-uploads "$HOME/core15-restored-uploads"

Restore отказывается использовать имя контейнера, отличное от supply-core15-restore*, БД кроме supply_core15_restore, PostgreSQL не версии 17, уже заполненную public или существующую папку целевых файлов. Проверка целостности выполняется до любых записей. Это страховка от случайного запуска поверх рабочего supply_manager. При сбое в процессе pg_restore тестовый контейнер считается частично восстановленным: для повтора **создать новый пустой изолированный контейнер и новую директорию**, не применять --clean к основной БД.

Скрипт сравнивает счётчики записей, ссылки на вложения и контрольные суммы файлов. Затем для ручной приёмки запустить **отдельный** API с копией вложений в его рабочем uploads, на другом порту и с тестовым URL:

    postgresql://supply_restore:<тестовый_пароль>@127.0.0.1:55443/supply_core15_restore?schema=public

Не направлять рабочий API на эту БД. В восстановленной среде проверить скачивание синтетических PNG и PDF под ADMIN/PROCUREMENT, запрет для EMPLOYEE без полномочий и 401 без сессии. Интеграции Telegram и почты должны быть отключены. Для копии реальных рабочих данных тестовая среда должна быть изолирована и иметь тот же уровень защиты доступа, что и оригинал.

## RPO/RTO и независимая приёмка

В Issue #59 зафиксировать:
- время прекращения записи, начала и завершения создания backup, время последнего успешного backup;
- фактический RPO как возможную потерю изменений относительно точки снимка;
- фактический RTO от запуска восстановления на чистой машине до проверки API и обоих вложений;
- размеры, количество файлов, проверенные счётчики, отрицательные тесты и отклонения;
- результат независимого восстановления Тимофеем на другой машине.

Скрипты не обещают RPO=0: между ручными снимками окно потери данных может быть произвольным. RTO также требует практического замера.

## Что остаётся до завершения полного CORE-15 (#36)

Этот PR обеспечивает основу #59, но ещё не решает: централизованный полный аудит входов, выдачи файлов и финансовых действий без секретов; HTTPS/TLS, secure cookie/CSRF/CORS за доверенным proxy, rate limits; отдельные роли БД с минимальными правами и ротацию секретов; автоматический защищённый backup с блокировкой параллельных запусков, расписанием, сроком удержания, шифрованием, внешним хранилищем, уведомлениями об ошибках и мониторингом; восстановление на другой машине и эксплуатационную UAT-подпись. Нельзя считать Issue #36 закрытым до этих шагов.

## Автоматические тесты

    node --test scripts/core15-snapshot.test.mjs

CI дополнительно создаёт два синтетических PostgreSQL 17, применяет текущие Prisma-миграции, создаёт запись заявки с PNG и КП с PDF, выполняет backup → verify → restore и отклоняет вторичное восстановление или повреждение dump. В CI не используется реальная рабочая БД, JWT или документы предприятия.
