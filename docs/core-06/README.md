# CORE-06 — Справочник поставщиков и полноценная работа с КП

Задача: [#27](https://github.com/HeiterX/Supply_Manager/issues/27). Ветка основана на CORE-05.

## Справочник поставщиков

- `Supplier`: название, нормализованное имя, ИНН (10/12 цифр), юридический адрес,
  реквизиты, контакт, телефон, email, сайт, категории, статус, ответственный,
  примечания.
- `SupplierChange`: действие, исполнитель, дата, snapshot до/после.
- `GET /api/v1/suppliers?q=...`: поиск, ограничение 100 результатов.
- `GET /api/v1/suppliers/:id`: история изменений, связанные КП и заказы.
- `GET /api/v1/suppliers/responsibles`: активные снабженцы и администраторы.
- `POST /api/v1/suppliers`, `PATCH /api/v1/suppliers/:id`: создание и обновление.

Права: только PROCUREMENT/ADMIN через JWT и RolesGuard; изменяющие
запросы защищены CSRF. Нет публичного поиска контрагентов.
Нормализация имени (пробелы, регистр, NFKC) и уникальность ИНН блокируют
новые дубли. Старые карточки сохранены без принудительного изменения;
при совпадении имени они переиспользуются, а ручное объединение старых
дублей оставлено на отдельную задачу (чтобы не переписать историю).

При создании КП `supplierId` выбирает существующего контрагента.
При передаче только `supplierName` проверяется справочник; новый
создаётся лишь при отсутствии совпадения. Редактирование КП **никогда
не изменяет реквизиты общей карточки поставщика**.

## Версии КП и финансовые данные

- `SupplierOffer`: supplierId, валюта (nullable), цена (nullable),
  срок действия, срок поставки, наличие, условия оплаты/доставки, версия,
  причина ручного выбора, исполнитель/дата решения.
- `SupplierOfferRevision`: неизменяемый снимок каждой версии и события
  выбора, с автором и временем.
- `SupplierOfferItem`: ссылка на TaskItem, количество, цена, валюта,
  наличие, примечания.
- `PATCH /api/v1/tasks/:taskId/supplier-offers/:offerId`: версия +1,
  старые snapshots не переписываются. `expectedVersion` защищает от
  потерянного обновления (HTTP 409). После создания заказа редактирование
  исходного КП запрещено, включая отменённые заказы.
- `PATCH /api/v1/tasks/:taskId/supplier-offers/:offerId/decision` с
  `{ "reason": "..." }`: явный выбор, причина от 10 символов, проверка срока,
  статуса поставщика и связанного заказа; записывается история.
- Новый многопоставочный заказ нельзя оформить до ручного выбора КП.
  После смены условий КП выбор надо подтвердить заново.
- Один Task может содержать несколько КП и несколько отдельных заказов;
  у каждого заказа сохраняются supplierId и supplierOfferId.

Точная стоимость позиции считается только из известной цены и валюты.
Валюта КП не подразумевается по умолчанию, если пришли новые строки с
ценой без явной валюты; агрегат остаётся null. Цена 0 — валидная
известная цена, null — неизвестная. Валюты не смешиваются и не
конвертируются автоматически. Для оформления заказов в текущей версии
допускаются только КП в RUB; КП в других валютах можно хранить и
сравнивать без ложной эквивалентности. Если доставка не указана, UI не
показывает придуманный итог.

## Документы КП

- `POST /api/v1/tasks/:taskId/supplier-offers/:offerId/documents`:
  multipart `file`, до 8 МБ, PDF/PNG/JPEG.
- `GET /api/v1/tasks/:taskId/supplier-offers/:offerId/documents/:documentId`:
  приватное скачивание только PROCUREMENT/ADMIN.
- Проверка магических байтов, соответствия расширению и MIME-типа.
  Случайное имя файлов, отсутствие публичного URL, заголовки no-store,
  nosniff, attachment, журнал загрузок.
- `SupplierOfferDocument`: версия КП, имя оригинала, размер, SHA-256,
  MIME, исполнитель, дата загрузки. Файл не заменяет предыдущую версию.
- Файлы сохраняются в `apps/api/uploads/offer-documents`. Этот каталог
  **должен быть постоянным volume и включаться в backup вместе с БД**.
  Не помещайте документы с реальными коммерческими данными в git.
- Документы не удаляются автоматически при новой версии КП.

## Миграция и тестирование

Миграция `20261123210000_core06_suppliers_offers` добавляет поля и
таблицы без удаления старых записей. Старые КП с известной суммой
помечены RUB, поскольку прежняя система была рублёвой.

```bash
cd apps/api
npx prisma generate
npm run lint && npm run build && npm run test:e2e
cd ../web
npm run lint && npm run build
```

`npm run test:e2e` проверяет `?schema=e2e` и применяет миграции
только к изолированной схеме. Не запускать `npx vitest` напрямую
на рабочей БД. На dev-базе — сначала бэкап, затем `npx prisma migrate deploy`.

Перед merge: ревью Тимофея, smoke-test на синтетических данных,
проверка прав и тома файлов. Порядок зависимостей: CORE-03 → CORE-04
→ CORE-05 → CORE-06. Принципиально без ИИ/OCR/ML.
