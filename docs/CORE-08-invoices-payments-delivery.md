# CORE-08 — Счета, частичные оплаты, доставка, приёмка и закрытие закупки

Связано с [CORE-08 #29](https://github.com/HeiterX/Supply_Manager/issues/29). Техническая ветка основана на [CORE-07 PR #50](https://github.com/HeiterX/Supply_Manager/pull/50), который включает CORE-04–CORE-06. Карточка использует действующие AppShell, AuthGate и API-клиент этой ветки. Перенос в рабочие экраны CORE-12/CORE-13 ожидает объединения зависимостей [PR #43](https://github.com/HeiterX/Supply_Manager/pull/43) и [PR #44](https://github.com/HeiterX/Supply_Manager/pull/44).

## Исходное состояние и архитектура

CORE-07 распределяет позиции по нескольким заказам. До CORE-08 в заказе хранились номер и дата одного счёта, а статус заказа отражал целую оплату, целую поставку и целую передачу. Теперь заказ сохраняет состав, сумму, поставщика и распределение. Для новых заказов с позициями его финансовое и физическое исполнение рассчитывается по связанным записям. Полный счёт и полный заказ можно оплачивать и принимать частями независимо.

- **Invoice / Payment** хранят счета и подтверждённые платежи. Поставщик счёта наследуется из заказа, заказ платежа — из счёта. Номера счёта уникальны в рамках заказа, подтверждения оплаты уникальны в рамках счёта. Отмена сохраняет исходные данные и причину в аудите.
- **Shipment / ShipmentItem** хранят партии, транспортные даты, перевозчика, трек-номер и состав. Внутри партии позиция заказа встречается один раз. Сумма действующих резервов партий проверяется по каждой строке заказа.
- **FulfillmentEvent** хранит приёмку, возврат, передачу, расхождение и его урегулирование. Событие связано со строкой заказа и при необходимости со строкой партии. Урегулирование ссылается на исходное расхождение.
- **FulfillmentOperation** связывает запись истории с закупкой, заказом, действием и автором. Хранит время, итоговый идентификатор и снимки. Это доменная история до появления общего аудита CORE-15. Экран показывает последние 100 операций, полная история сохраняется в БД.
- Привязка защищённого документа зарезервирована в метаданных счёта, платежа и складского события. Загрузка и выдача этих документов зависят от CORE-15. Существующие защищённые документы КП работают по собственному контракту.

Схема связей и порядок транзакции приведены в [диаграмме PlantUML](CORE-08-invoices-payments-delivery.puml).

## API

Базовый путь — /api/v1. Все маршруты требуют активную cookie-сессию. Изменения используют существующую CSRF-проверку.

| Метод и путь | Назначение |
| --- | --- |
| GET /tasks/:taskId/fulfillment | Суммы и статусы счетов, партии, показатели по позициям, препятствия закрытию, история и возможности текущей роли |
| POST /tasks/:taskId/orders/:orderId/fulfillment | Одна операция с обязательными action и key (UUID v4). Ответ 201 с id и replayed |
| PATCH /tasks/:taskId/orders/close | Закрытие закупки. Возвращает 200 или 409 с перечнем препятствий. Повтор после успешного закрытия даёт 409 |

| action | Поля операции |
| --- | --- |
| enable-ledger | Для исторического заказа в исходном состоянии требуется подтверждённая сверка перед включением учёта |
| create-invoice, edit-invoice | number, date, amount, currency; при изменении targetId; опционально dueOn и comment |
| approve-invoice, cancel-invoice | targetId счёта; при отмене comment с причиной |
| register-payment | targetId счёта, amount, currency, date, number подтверждения; опционально comment |
| cancel-payment | targetId платежа и comment с основанием корректировки |
| create-shipment | number, items с itemId строки заказа и quantity; опционально expectedOn и comment |
| dispatch-shipment | targetId партии, date, carrier; опционально trackingNumber и expectedOn |
| arrive-shipment | targetId партии и date |
| cancel-shipment, short-close-shipment | targetId партии, comment с основанием |
| receive, return | targetId строки партии, quantity и date; для возврата comment с причиной |
| handover | targetId строки заказа, quantity, date, comment с получателем |
| report-discrepancy | targetId строки партии, quantity, date, reason (SHORTAGE, DAMAGED, WRONG_ITEM, INCOMPLETE, OTHER); опционально comment |
| resolve-discrepancy | targetId расхождения, date, comment с решением |

Даты передаются в формате YYYY-MM-DD. Суммы и количества передаются десятичными строками. Повтор того же тела с тем же ключом возвращает исходный идентификатор результата. Ключ с изменённым телом даёт 409. DTO и проверка календарных дат возвращают 400. Отсутствующая сессия даёт 401, недостаточные права — 403, объект за пределами указанной закупки или заказа — 404, нарушение бизнес-инварианта — 409.

## Расчёты и переходы

- Сумма в RUB — Decimal(14,2). Оплачено = сумма действующих платежей. Остаток счёта = сумма счёта − оплачено. Сервер возвращает раздельно состояние согласования, состояние оплаты и признак просрочки на календарный день UTC. Нулевые, отрицательные и превышающие остаток платежи отклоняются. Валюта заказа следует ограничению CORE-07 на RUB.
- Финансовое обязательство считается исполненным, когда все действующие счета согласованы, оплачены и в сумме покрывают стоимость заказа. Это проверяемая матрица для технической приёмки. После регистрации любого платежа история счёта защищена, а платёж корректируется отдельным действием с причиной. Реальные переводы не инициируются.
- Партия резервирует точное количество Decimal(14,3). Полная отгрузка партии требует даты и перевозчика. Приёмка учитывается после фактического прибытия. Можно принять несколько частей. На уровне партии контролируется валовое принятое количество, на уровне заказа — количество за вычетом возвратов.
- Возврат ограничен остатком реально принятого товара в партии и доступным остатком по строке заказа после передачи. Возврат освобождает объём для замены. Недопоставленную партию можно закрыть после фиксации недостающего количества каждой неполной строки. Сама потребность остаётся открытой до восполнения или отдельно утверждённой процедуры.
- Количества в карточке: запрошено, заказано, не заказано, отгружено, получено, возвращено, принято, передано, осталось выполнить. Отгружено и получено отражают валовое движение и могут превышать количество заказа после замены. Принято = получено − возвращено. Осталось выполнить = запрошено − передано. Платёж распределяется по счетам, распределение денег по позициям ждёт согласования.
- Закрытие проверяет действующие заказы, полный объём исполнения и передачи, отсутствие незавершённых партий, неоплаченных обязательств и открытых расхождений. Политика обязательных документов зависит от CORE-15 и согласования с владельцем процесса. Выставление счёта, движение денег, отгрузка и приёмка имеют независимые источники фактов.
- Создание или изменение заказа, отмена, запись счета, платежа, партии, приёмки и проверка закрытия сериализуются одной блокировкой строки Task. Проверки выполняются внутри изменяющей транзакции, а журнал пишется до её фиксации. Для записей в БД добавлены внешние ключи, уникальность и ограничения положительных сумм и количеств.

## Права и вопросы для Максима

| Роль | Возможности |
| --- | --- |
| EMPLOYEE | Работает со своими заявками по CORE-03/04. API закупок и финансов недоступны |
| PROCUREMENT | Просмотр закупок отдела, оформление счетов, партий, приёмки, возвратов, передачи и закрытия по серверной матрице |
| ADMIN | Те же операции. Для технической приёмки флаг CORE08_FINANCE_ENABLED=true открывает согласование счетов и регистрацию/корректировку платежей только ADMIN. По умолчанию финансовые записи отключены |

Для бизнес-приёмки Максим подтверждает финансовые полномочия, документы и процедуру подтверждения факта оплаты, правила округления/авансов, итоговую матрицу закрытия и допустимые исключения, способы окончательного урегулирования недопоставки и возврата, распределение платежей по позициям. Согласование является условием включения финансовых записей на рабочей среде.

## Миграция и исторические заказы

20261125120000_core08_fulfillment — аддитивная миграция. Старые заказы сохраняют статусы и все исходные поля. Включение нового учёта не создаёт фиктивных оплат или приёмок. Исторические заказы, по которым уже началось исполнение, остаются в прежнем сценарии до сверки по первичным документам и отдельно утверждённой процедуры переноса. Включение в интерфейсе возможно для заказа с позициями, исходным статусом ORDERED и без отметок оплаты/отгрузки/приёмки/передачи. Старый номер счёта показывается для сверки. После включения полного учёта paidAt и receivedAt означают соответственно полное закрытие финансового обязательства и полную текущую приёмку.

Проверено на отдельном PostgreSQL 17. Prisma migrate deploy применил все миграции в чистой схеме e2e. В другой схеме той же тестовой БД проверено обновление цепочки CORE-07 с сохранением синтетического исторического заказа, номера счёта, суммы, paidAt и receivedAt. Новые таблицы не получили фиктивных записей.

## Проверки и пользовательская приёмка

- API unit: точная арифметика копеек, отмена платежей, дата просрочки и количество с тремя знаками. API E2E: заявка сотрудника, принятие, два КП и заказа, частичные/конкурентные платежи и приёмка, повторы, возврат, недопоставка, права доступа и закрытие.
- Web Playwright: карточка закупки с реальным API и PostgreSQL, счёт, оплата 50 из 150, приёмка 1 из 3, блокировка закрытия, оплата остатка, полная приёмка, передача и закрытие. Проверены desktop 1440×980 и mobile 390×844.
- Для API используйте npm ci, npx prisma generate, npm run lint, npm run build, npm test и npm run test:e2e. Тестовая конфигурация обязательно использует отдельную PostgreSQL с ?schema=e2e.
- Для браузера после npm ci в apps/web установите Chromium командой npx playwright install chromium. Запустите API на localhost:4080 с CORE08_FINANCE_ENABLED=true, FRONTEND_ORIGIN=http://localhost:4081 и тестовым DATABASE_URL. Соберите и запустите Web на localhost:4081 с NEXT_PUBLIC_API_URL=http://localhost:4080/api/v1. Выполните npm run test:e2e в apps/web с тем же тестовым DATABASE_URL. CORE08_CHROMIUM_CHANNEL=chrome позволяет использовать локальный Chrome.
- Для ручной проверки откройте «Заказы» в карточке синтетической закупки. Создайте счёт, согласуйте его в уполномоченной сессии, проведите две части оплаты. Создайте две партии, отметьте прибытие и примите их по отдельности. Убедитесь, что до приёмки, передачи и урегулирования расхождений закрытие недоступно. После закрытия проверьте историю и остатки.
