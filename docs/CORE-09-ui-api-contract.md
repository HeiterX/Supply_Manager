# CORE-09 — реализованный интерфейс и серверный контракт

Обновлено 26.11.2026. Основание: Issue #30, Supply Manager Core v3.0 от 19.11.2026. Код: `feature/core-09-unified`, единый PR #64. Публичные маршруты ниже относительно `/api/v1`; все используют cookie-JWT, CSRF для изменяющих операций и серверный RBAC.

## Основные сущности

- `NextAction`: одно активное действие для закупки (partial unique PostgreSQL index); завершённые действия сохраняются в истории и допускают новое активное действие. Отдельные `title`, `assigneeId`, `dueAt`, `reminderAt`, `version`, `status`. Срок закупки `Task.deadline` не подменяет срок конкретного действия.
- `NextActionHistory`: структурированные события CREATED / ASSIGNED / RESCHEDULED / UPDATED / COMPLETED / CANCELLED с исполнителем и временем.
- `NextActionNotification`: персональная запись с `readAt`, `eventKey` и уникальностью на получателя.
- `NextActionScheduleReceipt`: уникальная пара action/version/kind; предотвращает повторное создание события после сбоев и при нескольких workers.
- `NextActionMutation`: идемпотентные изменения по ключу (UUID), отпечатку тела и сохранённому ответу.

Аддитивная миграция `20261126120000_core09_next_actions` сохраняет существующие закупки. Для незакрытых legacy-закупок создаётся активное действие **без выдуманного ответственного и срока**; `Task.reminderAt` переносится, если было задано. После миграции администратору необходимо назначить ответственных и сроки, иначе гарантия «каждое действие имеет ответственного и срок» не выполнена для старых записей.

## API

| Метод и маршрут | Назначение |
|---|---|
| `GET /next-actions?scope=mine&filter=all&q=&page=1&limit=20` | Действия и авторитетные серверные счётчики; поддерживает `scope=unassigned`, `scope=all` только ADMIN |
| `GET /next-actions/by-task/:taskId` | Текущее активное действие или null; также `lastActionId` для истории завершённого |
| `POST /next-actions/by-task/:taskId` | Создание следующего действия только если нет активного |
| `GET /next-actions/assignees` | Минимальный список активных PROCUREMENT/ADMIN для формы назначения |
| `GET /next-actions/:id/history` | Последние 200 структурированных событий действия |
| `PATCH /next-actions/:id` | Изменение с `If-Match: "<version>"`, `Idempotency-Key: UUID`; 409 для устаревшей версии |
| `POST /next-actions/:id/complete` | Выполнение и сохранение истории, версия и ключ идемпотентности обязательны |
| `GET /notifications?filter=all&page=1&limit=20` | Персональные уведомления, полный `unreadCount` |
| `PATCH /notifications/:id/read` | Идемпотентное прочтение, чужое уведомление не раскрывается |

Фильтры: `all`, `today`, `overdue`, `waiting_supplier`. Статусы считаются **на сервере**. OVERDUE при `dueAt < now`; TODAY при `now <= dueAt < конец дня` в `Europe/Moscow`; WAITING_SUPPLIER при открытом запросе КП и отсутствии более высокого приоритета срочности. Счётчики считаются до текстового поиска и выбранного фильтра, `total` — после них. `page` начинается с 1, `limit` от 1 до 100.

## Роли и безопасность

- EMPLOYEE не имеет доступа к персональным закупочным действиям.
- PROCUREMENT видит собственные действия и отдельную очередь неназначенных. Изменять назначенное другому действие нельзя. Из неназначенного можно взять себе.
- ADMIN видит все действия, может переназначать и снимать назначение; назначить можно лишь ACTIVE PROCUREMENT/ADMIN.
- При смене ответственного прежнему получателю больше не выдаются уведомления об этом действии, а очередь ещё не отправленных Telegram сообщений инвалидируется.
- Изменения и выполнение сериализуются PostgreSQL row lock + version check; случайная повторная отправка с тем же ключом возвращает предыдущий ответ, с другим телом — 409.
- Нет автоматического массового назначения legacy-закупок и раскрытия чужих документов/файлов.

## Напоминания и Telegram

`NextActionsService` проверяет подлежащие исполнению события раз в 60 секунд, пока запущен API. При `reminderAt <= now` создаёт ACTION_DUE, при `dueAt < now` — ACTION_OVERDUE (не чаще одного раза за московский календарный день на версию действия). Запись уведомления, receipt и публикация в уже существующий транзакционный CORE-10 outbox происходят атомарно. Дубли подавляются по action/version/kind (для просрочки kind включает календарный день); после переноса версия меняется и старые PENDING доставки отменяются. Перед фактической отправкой повторно проверяются версия, назначение, доступ и состояние закупки. Сбой Telegram не откатывает закупку; Bot API не обеспечивает внешнюю exactly-once доставку.

## UI

Маршруты `/actions` и `/notifications` встроены в актуальный Workspace CORE-12/13/14, виджеты и адаптер UI взяты из закрытого PR #40 Тимофея. В карточке закупки есть редактирование, назначение, завершение, новое действие и история. Уведомления доступны через bell, список и серверное прочтение; polling 60 секунд при активной вкладке. Старый `Task.nextAction` остаётся **подсказкой статуса закупки** в legacy API и не считается новым структурированным действием.

## Ограничения перед бизнес-приёмкой

- Рабочие календари, праздничные дни и configurable SLA не внедрены; границы дня — Europe/Moscow (UTC+3). При требованиях к другим регионам нужен отдельный configurable time zone.
- Неполные legacy-действия нужно заполнить вручную. Срок/ответственный не могут быть достоверно рассчитаны из старого `Task.deadline`.
- Не реализованы Web Push/SSE, почтовый канал и внешний scheduler, живущий независимо от API. Напоминания опаздывают, если API выключен, но догоняются после его запуска.
- Требуются ревью, браузерная проверка и ручной smoke test после CI. Не запускать миграции на реальной базе без резервного копирования.

## Проверка

CI — lint, build, unit, E2E на изолированной схеме `e2e`. Новый `test/core09-next-actions.e2e-spec.ts` проверяет роли, ownership, передачу, concurrency/version, идемпотентность, дедуп расписания, чтение и завершение. Предшествующий фикс `fix/core-09-preserve-reminders` включён в единый PR #64.
